# Deterministic credit processing architecture

## Runtime boundary

New report audits and response reviews use three explicit stages:

1. **Extraction:** model calls use `creditExtractionSchemas.js` and `extractionPrompts.js`. They may transcribe displayed values, field states, page references, and response statements only.
2. **Evaluation:** `deterministicAudit.js` and `deterministicResponse.js` own account matching, cross-bureau comparisons, Metro 2 rules, demand matching, response windows, classifications, and legacy-shape adapters.
3. **Narrative:** letter model calls receive only authorized `FLAG` findings or reviewed response findings. They may phrase those findings but cannot create, remove, reclassify, or prioritize them.

## Compatibility contract

- Existing saved audits and responses remain readable.
- New audit records retain the legacy `accounts[].violations` shape, generated from deterministic `FLAG` findings, so existing campaign and letter rendering paths continue to work.
- `REVIEW_REQUIRED` findings are stored in `accounts[].findings` and shown to staff, but are excluded from letter inputs and campaign targets.
- New response analyses retain the legacy `classification`, `demandAnalysis`, `admissions`, and `phase3Leverage` fields, generated by deterministic code.
- No database migration is required because schema versions and provenance are stored inside existing JSON columns.

## Missing-field safety

Extracted report fields use four states:

- `PRESENT`
- `EXPLICITLY_BLANK`
- `NOT_SHOWN`
- `UNREADABLE`

Rules that depend on a missing mandatory value may fire only for `EXPLICITLY_BLANK`. `NOT_SHOWN` and `UNREADABLE` never become automatic violations.

## Schema versions

- Report audit: `deterministic-audit-v1`
- Response analysis: `deterministic-response-v1`
- Extraction contract: `credit-extraction-v1`

Add new rules by assigning stable rule IDs and fixture tests. Do not place substantive evaluation instructions or output fields back into extraction prompts or schemas.
